# PRD-0003: Deepen the Configuration Module

## Problem

`RefitGeneratorSettings` is a **god object** with ~80 properties across 642 lines. Settings flow through five modules before reaching the generator, each adding a layer of transformation:

```
CLI Settings (Spectre.Console.Cli)
  → ConventionMapper (reflection-based property copy)
  → SettingsMapper (manual boolean/enum mapping)
  → SettingsValidator (validation + defaults)
  → RefitGeneratorSettings (642-line POCO)
```

### Friction points

- **Bouncing**: Understanding one settings rule (e.g., "how does `--no-auto-generated-header` become `settings.AddAutoGeneratedHeader = false`?") requires bouncing between `Settings.cs`, `ConventionMapper.cs`, `SettingsMapper.cs`, and `RefitGeneratorSettings.cs`.
- **Shallow modules**: `ConventionMapper` (32 lines) and `SettingsMapper` (46 lines) are pass-throughs — they copy properties without adding behavior. Deleting them moves complexity to callers, not concentrates it.
- **No single source of truth**: Settings precedence rules (CLI args override settings file, which overrides defaults) are scattered across `SettingsValidator`, `GenerateCommand`, and `OutputPlanner`.
- **`OutputPlanner` is pure path-computation logic** that directly inspects `RefitGeneratorSettings` properties. It could be collapsed into `GenerationOrchestrator` but exists separately.

### Deletion test

If you delete `ConventionMapper` and `SettingsMapper`, complexity reappears across CLI, MSBuild, and Source Generator — they each need to know how to map their settings format to `RefitGeneratorSettings`. This signals these modules were **earning their keep** only as a consolidation point.

## Current Architecture

### Three distribution forms, three settings formats

| Distribution form | Settings format | Mapping chain |
|---|---|---|
| CLI | `Settings` (Spectre.Console.Cli) | CLI → ConventionMapper → SettingsMapper → RefitGeneratorSettings |
| MSBuild | `.refitter` JSON file | File → Serializer.Deserialize → RefitGeneratorSettings |
| Source Generator | `.refitter` JSON file | AdditionalText → Serializer.Deserialize → RefitGeneratorSettings |

### `RefitGeneratorSettings` composition

The settings class uses nested config objects to organize ~80 properties:

```csharp
public class RefitGeneratorSettings
{
    private readonly OpenApiSourceConfig openApiSource = new();      // OpenApiPath, OpenApiPaths
    private readonly CodeGenerationConfig codeGeneration = new();    // Namespace, contractsNamespace, etc.
    private readonly ParameterConfig parameterConfig = new();        // Parameter-related settings
    private readonly OutputConfig outputConfig = new();             // Output folder, filename, etc.
    private readonly TypeConfig typeConfig = new();                 // Type accessibility, suffix, etc.
    private readonly FilterConfig filterConfig = new();             // IncludeTags, IncludePathMatches
    private readonly SchemaConfig schemaConfig = new();             // TrimUnusedSchema, KeepSchemaPatterns
    private readonly FeatureConfig featureConfig = new();           // GenerateClients, GenerateContracts, etc.
    private readonly DependencyInjectionSettings dependencyInjectionSettings;
    private readonly ApizrSettings apizrSettings;
    private readonly CodeGeneratorSettings codeGeneratorSettings;
}
```

**Problem**: The public interface still exposes all ~80 properties directly. Callers must know every property to configure generation. The nested objects are implementation details, not part of the interface.

### `OutputPlanner` (161 lines)

Pure path-computation logic. Decides where generated files are written based on CLI args vs. settings file. No side effects. Could be collapsed into `GenerationOrchestrator`.

**Current interface**: Four static methods, each taking `Settings` + `RefitGeneratorSettings` and computing a path.

**Problem**: Callers must know about both `Settings` (CLI) and `RefitGeneratorSettings` (core). The path-planning rules are spread across multiple static methods with complex branching logic.

## Proposed Solution

### Deepened module: `SettingsResolver`

A single module that owns all settings precedence rules. It takes CLI args and settings file content as inputs and produces a validated `RefitGeneratorSettings`.

```csharp
public static class SettingsResolver
{
    /// <summary>
    /// Resolves settings from CLI arguments and an optional settings file.
    /// CLI arguments override settings file values, which override defaults.
    /// </summary>
    public static RefitGeneratorSettings Resolve(
        IReadOnlyDictionary<string, string> cliArgs,
        string? settingsFilePath,
        string? settingsFileContent,
        string? baseDirectory);

    /// <summary>
    /// Resolves settings from a .refitter file content only (used by MSBuild and Source Generator).
    /// </summary>
    public static RefitGeneratorSettings ResolveFromFile(
        string settingsFilePath,
        string settingsFileContent,
        string? baseDirectory);
}
```

**Interface**: Two methods. No knowledge of CLI argument parsing, file I/O, or validation internals.

**Error modes**: Throws on invalid settings (missing required fields, invalid enum values, etc.).

**Ordering**: Sequential — resolve defaults → apply file settings → apply CLI overrides → validate.

**Config**: Base directory for resolving relative paths.

### Deepened `RefitGeneratorSettings` interface

Narrow the interface by moving configuration through the resolver:

```csharp
// Instead of:
settings.OpenApiPath = "openapi.json";
settings.Namespace = "MyApp";
settings.GenerateMultipleFiles = true;

// Callers use the resolver:
var settings = SettingsResolver.Resolve(
    cliArgs: new Dictionary<string, string> { { "namespace", "MyApp" } },
    settingsFilePath: "config.refitter",
    settingsFileContent: File.ReadAllText("config.refitter"),
    baseDirectory: ".");
```

The `RefitGeneratorSettings` class itself stays as-is (642 lines of POCO). The deepening is at the **seam** — callers interact with `SettingsResolver` instead of directly manipulating `RefitGeneratorSettings`.

### `OutputPlanner` consolidation

Move path-planning logic into `RefitGeneratorSettings` as a method:

```csharp
public class RefitGeneratorSettings
{
    /// <summary>
    /// Computes the output path for a generated file.
    /// Resolves relative paths against the settings file directory.
    /// </summary>
    public string ResolveOutputPath(string relativePath, string? baseDirectory)
    {
        // Current OutputPlanner logic
    }
}
```

This eliminates `OutputPlanner` as a separate module and concentrates path-planning logic with the settings that determine it.

## Benefits

### Locality

- All settings precedence logic in one place (`SettingsResolver`)
- Path-planning logic concentrated in `RefitGeneratorSettings` (where the data lives)
- Changes to precedence rules don't touch CLI, MSBuild, and Source Generator separately

### Leverage

- One resolver module pays back across all three distribution forms (CLI, MSBuild, Source Generator)
- Callers learn `SettingsResolver.Resolve()` instead of knowing about `ConventionMapper`, `SettingsMapper`, `SettingsValidator`, and `OutputPlanner` separately

### Test improvements

- **Before**: Test settings precedence by testing each mapper/validator separately. No single test covers the full precedence chain.
- **After**: One test surface (`SettingsResolver.Resolve()`) with tests for each precedence level (defaults → file → CLI). Test the full chain in one place.
- **New test surface**: Test precedence rules without parsing CLI args or reading files. Pass settings as dictionaries and strings.

## Trade-offs

- **Added complexity**: One new module for settings that works today. The current five-module chain is distributed but functional.
- **Justification**: The five-module chain is a pass-through pattern. Each module does a tiny transformation (copy properties, map booleans, validate, compute paths). Consolidating into one deep module eliminates the bouncing between modules.
- **Risk**: Medium. `RefitGeneratorSettings` has ~80 properties — the resolver must handle all of them correctly. Extensive testing needed.
- **Breaking change**: Yes. CLI, MSBuild, and Source Generator all need to switch from their current mapping logic to `SettingsResolver`.

## Testing strategy

1. **Precedence tests**: Test defaults → file → CLI precedence for each settings category
2. **Validation tests**: Test error modes (missing required fields, invalid enums, etc.)
3. **Path resolution tests**: Test relative path resolution against settings file directory
4. **Migration tests**: Verify CLI, MSBuild, and Source Generator produce identical settings from the same inputs
5. **Existing tests**: Update `SettingsFile/` tests to use `SettingsResolver`

## Notes

- This deepening **contradicts** the current architecture where settings mapping is distributed across multiple mappers. But the deletion test confirms these modules are earning their keep only as a consolidation point.
- The `RefitGeneratorSettings` class itself (642 lines) stays as-is. The deepening is at the **seam** — how callers configure it, not its internal structure.
- This deepening makes `RefitGeneratorSettings` **more testable** and **less coupled** to CLI-specific concerns, which aligns with the overall goal of deepening the `RefitGenerator` module (PRD-0001).
- The `OutputPlanner` consolidation is lower priority — it's pure path-computation logic with no side effects. It can be done separately if needed.
